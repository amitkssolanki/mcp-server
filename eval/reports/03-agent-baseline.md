server connected but exposed 0 tools, because MCP SDK 1.1.0 accepted

model wrote tool calls as prose, and in one probe invented a result (6
cancelled 2018 orders; the oracle says 334). The server was pinned to
2025-11-25 (`2886c77`) and the runner now fails any run that does not see
exactly the nine read tools (`8c983e1`). The day 2 fingerprint was unchanged
(`f4841a48894b268d`). This report is the fresh run after both commits; no
aborted run is counted in it.

**Result: at the ceiling.** 45 of 45 answers agree with the oracle. Each run
made exactly one tool call, to an acceptable tool with arguments that pass
the pre-registered rule. Across 3 runs, tool choice varied only where two
tools are both right (A04, A05: `list_categories` vs
`revenue_report(category)`).

**The one inconsistency is arithmetic.** A09 asks for the overall late
rate, which no tool reports. All three runs read the band counts correctly
and wrote "7,645 out of 96,470". Two then answered 7.93 and one 7.9; the
correctly rounded value is 7.92 (7.9247%). All three are within the
pre-registered 0.1-point tolerance, so they are graded correct, but 7.93 is
the model's division, not the data.

**The model never saw the text content.** Every tool result in all 45 runs
was the `structuredContent` JSON. Claude Code 2.1.284 passes that to the
model instead of the text content. What the tools say only in text did not
reach the agent. That covers "Revenue is items plus freight, from completed
orders", "Order counts are not summed", "Negative AVG LATE means early", and
the fence that labels customer-written review text as data, not
instructions. The model answered correctly from field names alone (`revenue`,
`item_revenue`, `late_orders`).

**Limits.** One model (`claude-sonnet-5`), one client version (2.1.284),
three runs per question, no control over sampling temperature. 15 questions
is an engineering sample, not a benchmark.
